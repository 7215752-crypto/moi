# Логика расчёта ЗП — «одна кнопка» (целевая)

Статус: черновик, утверждается владельцем по кускам. Обновлять этот файл при каждом решении.
Последнее обновление: 2026-08-04.

## Суть

Менеджер ресторана заходит в портал, выбирает период (полмесяца, портал предлагает последний),
нажимает **«Рассчитать зарплату»**. Портал сам собирает все данные и выдаёт готовую таблицу
расчёта — аналог Google-файла «ЗП Brisket+Pastrama» (секция на ресторан, строка на сотрудника,
компоненты в колонках, «К выдаче», ИТОГО). Никакой ручной сборки по шагам.

Каждый запуск кнопки = новая версия `payroll_runs` (период × ресторан). Старые версии
сохраняются, можно сравнить, что изменилось.

## Что делает кнопка (по порядку)

1. **Явки из iiko** — фактические часы: кто, в какой день, во сколько пришёл/ушёл.
   Уже работает: `/api/iiko-attendance` (импорт с сопоставлением имён через `employee_aliases`,
   автосозданием сотрудников и проверкой ставок).
2. **Сверка с графиком** — план из Google-таблицы (`planned_shifts`) против факта из iiko:
   опоздания (минуты), неявки, выходы вне графика.
   График **не влияет на оплату** — оплачиваются часы как в iiko; сверка нужна только чтобы
   понятно показать, сколько раз и на сколько человек опоздал (KPI). ← решение от 04.08.2026
3. **Продажи из iiko** — продажи блюд по каждому сотруднику → процент от продаж + фикс за блюда.
4. **Начисления** — часовая ставка × часы (или оклад за смену / месяц), сервисный сбор,
   шифт-лидерские (из подтверждённых `leader_shifts`).
5. **Покупки в зп** — расходные накладные из iiko, оформленные на сотрудника
   (сотрудник набрал товар в счёт зарплаты) → удержание из выплаты. ← решение от 04.08.2026
6. **Внешние строки** — штрафы/премии, официалка/инвентаризация: источник пока прежний,
   см. открытые вопросы.

## Галочки «выплачено» (защита от двойной выплаты)

- У каждой строки сотрудника — галочка «выплачено»: кто поставил и когда, снять может только owner (след остаётся в истории).
- Пока галочка стоит — строка заморожена, повторная «выдача» невозможна.
- Счётчик над таблицей: «Выплачено N из M — осталось выдать X ₽» (аналог строки «НАДО» в файле).
- Если после выплаты появился пересчёт и сумма изменилась — портал подсвечивает разницу
  («выплачено 52 957, по новой версии 53 100 — доплата 143 ₽»), выплаченное не теряется.

## Карточка сотрудника (клик по строке)

- Разбор суммы: все компоненты начислений/удержаний.
- Календарь смен «план против факта»: поставлен в 10:00, пришёл в 10:07 → опоздание 7 мин.
- KPI за период: часы, число и сумма опозданий, продажи, средний чек, шифт-лидерские смены.

## Светофор проблем (после каждого расчёта)

- Есть часы — нет ставки.
- Стоял в графике — нет явки (возможный прогул).
- Явка вне графика.
- Отрицательная сумма к выдаче.

## Реализовано в портале (04.08.2026)

- Страница периода перестроена «как файл ЗП»: секции по ресторанам, колонки-компоненты
  (часы, по ставке, % от продаж, фикс, сервисный, премии, штрафы, покупки, официалка,
  шифт-лидер), «К выдаче», итоги; версия расчёта берётся по каждому ресторану.
- Галочки «выплачено»: таблица `payroll_payouts` (unique период × ресторан × сотрудник —
  двойная выплата невозможна на уровне базы), ставят owner/accountant/manager, снимает
  только owner; счётчики «выплачено N из M · осталось X» на странице; при пересчёте
  после выплаты показывается «доплата/переплата».
- Кнопка «Рассчитать зарплату» на странице периода (owner/accountant/manager):
  пока забирает явки из iiko и обновляет часы; полный движок начислений — следующий этап.
- Явки хранят времена прихода/ухода (`first_in`/`last_out`); карточка сотрудника
  показывает «Смены и опоздания»: план против факта по дням, опоздания в минутах,
  неявки, смены вне графика. Роль manager получила доступ на чтение данных расчёта (RLS).
- Полировка по отзыву владельца (04.08.2026): под названием каждой колонки — источник
  данных («явки iiko», «бонусы iiko», «чеки iiko», «накладные iiko», «вручную») с
  тултипами; суммы в сводной таблице — целые рубли; источники строк в листке — по-русски.

## Решено (история)

- 05.08.2026 (вечер) — сверка портала с Google-файлом за 16–31.07, решения владельца:
  1) пороги шкалы процентов — по каждому ресторану отдельно (не на общую выручку человека);
  2) Шарипова — почасовая 300 ₽/ч с 16.07 (shift-ставка 4000 закрыта 15.07);
  3) Жуманийозов — 420 ₽/ч (в базе было 440, исправлено);
  4) смены бар/зал делить: официант в барную смену получает 2% (не шкалу), почасовку
     370 — только за барные смены (Заглядимов). Автоисточника ролей смен нет: в iiko
     явки Заглядимова идут ролью «Менеджер», в planned_shifts все смены «Зал» —
     ждём пометки барных смен в Google-графике, затем реимпорт графика и явок,
     ставку Заглядимова перевести на департамент «Бар». Код деления уже задеплоен;
  5) сотрудник с должностью не-официант/бармен процент не получает (кейс Новиковой:
     управляющая с явками в зале получала 4% — исправлено, запись удалена).
  Разобрано позже тем же вечером: 36 745,22 у Казариной — продажи её зальной смены
  28.07, они ВХОДЯТ в общие 123 587,72 → в файле % за этот день посчитан дважды
  (переплата 734,90). Портал: 2% от всей суммы один раз + почасовка 370 только за
  барные смены (78,35 ч = 28 989,50, зальный день без оплаты; ставка Казариной —
  hourly 370 с department «Бар» BMB, план 28.07 поправлен на «Зал» вручную).
  3 385 у Михайлова — НЕ штраф: в файле стоит в «Фикс блюда» и прибавляется
  (сверено по «К выдаче»), портал начислил так же. Остаётся: «госпожа бмб» 100 000 —
  ручная строка файла, в портале такого сотрудника нет; Заглядимов ждёт пометки
  барных смен в графике (в импорте все его смены «Зал»).
  Починен импорт графика: имена матчятся без учёта порядка слов (раньше терялись
  Голозубова/Казарина/Шаторная — «Наталья Казарина» ≠ «Казарина Наталья»).

- 05.08.2026 — «% от продаж» считает портал (раньше колонка была пустой — готовых
  бонусов процента в iiko нет). Формула вскрыта из PDF «Система мотивации BMB BRISKET»
  и сверена до копейки по официантам и барменам. База личной выручки подтверждена
  прогоном OLAP: WaiterName × DishDiscountSumInt (кто пробил позицию, сумма со скидкой),
  контрольное число Голозубовой 709 845,68 совпало на диапазоне 01–15.07 (в файле
  стоял первый полупериод). OrderWaiter.Name и DishSumInt дают другие числа — не база.
  Импорт extras пишет: % → iiko_motivation_records, фиксы блюд → manual_adjustments
  (iiko_fixed_bonus, колонка «Фикс блюда»). Возможное изменение шкалы барменов —
  владелец «разбирается с барменом» (пока плоские 2%).

- 05.08.2026 — сервисный сбор: в форме распределения добавлены кнопки-подсказки
  «По чекам (кто пробил)» (сбор каждого чека — официанту чека, резолв имён через

  «Очистить». Менеджер по-прежнему может править суммы руками — сохраняется
  только то, что в полях ввода.

- 04.08.2026 (вечер) — структура раздела «Сотрудники» (решение владельца):
  период-центричная навигация. «Сотрудники» → список периодов (+создание периода);

  и менеджеру (даты подставляются из периода, руками не вводятся).
  Аналитика по сотрудникам — ОТДЕЛЬНЫЙ раздел (не в периодах): средний чек,
  количество вложений, прибыль на человека, сравнение с коллегами по заведению/роли/

  пока не строим.
